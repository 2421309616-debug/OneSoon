# 派单策略设计

> 本文只回答一个问题：**一笔订单，为什么派给这个司机？**
>
> 依据：滴滴出行《用车服务分单算法》公示文档（网信算备 110108225375401230017 号）。

## 一、设计依据

滴滴文档里有三句话，把派单这件事说透了：

> **「根据司机接驾距离就近分配是滴滴派单的最大原则」**

> **「接驾距离指的是乘客发单点和司机所在位置之间的『路面距离』，路面距离是由导航系统计算，结合路网、路况信息综合规划出的路线的长度。所以即使乘客就在马路对面，如果司机师傅需要去远处掉头才能接到乘客，路面距离可能也会很远。」**

> **「若距离相同，则会派给口碑值分数更高的司机。」**

第三句是关键：**口碑值是 tiebreak，不是权重**。

这意味着派单不是"按分数加权抽签"，而是"先按接驾时间排序，一样快的时候才看口碑"。

## 三、核心目标

滴滴文档的原话：

> 「在考虑时间、距离等客观限制条件以及司机和乘客公平性感知的情况下，尽可能满足更多乘客和司机的体验需求，实现乘客打车成功率和司机接单收入的最优。」

翻译成我们的场景：

| 目标 | 怎么衡量 |
|---|---|
| 乘客少等 | 从发单到司机到达的平均时长 |
| 司机有单 | 每个在线司机每天的接单数分布 |
| 公平 | 先来的订单先派、没人被长期跳过 |

## 四、四步流程

严格对应滴滴文档的四步。

```
第一步 · 配对
  等待中的订单 × 在线司机 → 若干个「订单-司机」对

第二步 · 过滤
  按规则剔除不符合要求的对

第三步 · 算分
  给每个「订单-司机」对打分

第四步 · 匹配
  订单与司机一一匹配，得到最终结果
```

### 4.1 配对

- 订单：状态为「寻找司机」的实时单 + 到时间的预约单
- 司机：状态为「在线」且位置在 60 秒内更新过的

### 4.2 过滤

**分两部分：现在做的 4 条，和留给以后的 4 条。**

现在做的（`apps/server/dispatch/funnel/filter.ts`）：

| 规则 | 说明 | 状态 |
|---|---|---|
| 不重复推 | 同一笔订单只推给同一司机一次 | ✅ `already-offered` |
| 不超载 | 司机手上最多 3 单；满了不再推新单，但已推的仍显示到过期 | ✅ `too-many-orders` |
| 位置新鲜 | 超过 60 秒没上报位置的司机不参与 | ✅ `stale-location` |
| 粗筛 | 直线距离 > 10 km 直接排除（给将来接高德 API 省调用量） | ✅ `out-of-range` |

留给以后的（滴滴文档里有，我们还没做，见 9.3）：

| 规则 | 说明 | 状态 |
|---|---|---|
| 车型匹配 | 快车司机不可接专车订单 | ⏳ 待实现 |
| 预约/实时 | 只听预约单的司机，过滤掉实时单 | ⏳ 待实现 |
| 顺路方向 | 设了顺路目的地的司机，只接顺路的订单 | ⏳ 待实现 |
| 限行限号 | 保证司机接单后不会经过限行区域 | ⏳ 待实现 |

后 4 条需要的数据（车型、司机偏好、顺路目的地、限行规则）现在库里都没有，属于**未来设计**。

### 4.3 算分

滴滴文档：「主要根据订单和司机距离及司机口碑值等因素，计算『订单-司机』对的分数，**距离是影响分数的最大因素**」

我们的分数：

```
分数 = 接驾时间（分钟）
```

**只有一个主因素**。口碑值不参与算分，只做 tiebreak（见 4.4）。

为什么不用加权求和？

因为加权求和需要定系数（距离占多少、口碑占多少），而系数一旦定死，就会出现"3 公里外的 5.0 分司机压过 200 米的 4.8 分司机"——乘客白等。

排序天然解决了这个问题：先比时间，时间一样才比口碑。

### 4.4 匹配

**按订单等待时长排序，逐个分配。**

```
for 订单 in 等待中的订单（按等待时长降序）:
    if 30 秒内还有 pending 的推送:
        continue    # 上一位司机还没回应，让他看完这 30 秒

    候选 = 过滤后的司机
    按 ETA 分档 A / B / C / D

    for 档 in [A, B, C, D]:
        同档 = 该档的司机
        if 同档 为空: continue

        最快 = min(同档.ETA)
        同档 = [d for d in 同档 if d.ETA - 最快 < 1 分钟]
        同档.sort(key = (服务分降序, 今日接单数升序))

        选中 = 同档[0]
        推送(订单, 选中)
        break
```

**「最近 30 秒推过吗」怎么判**：只看 30 秒内、处于 `pending` 的那条推送。

推出去还挂着（`pending`）→ 说明这位还没回应，按 30 秒节奏走，下一轮再说。
推送已经结束（`rejected` / `expired`）→ 这一轮的结果已经定了，不必再等满 30 秒，**下一次 tick 就换人**。

所以换人有两种触发方式：

| 情况 | 什么时候换下一位 |
|---|---|
| 司机看到推送但不接（`pending` 挂满 30 秒） | 满 30 秒后的下一个 tick |
| 司机点了「拒绝」（`rejected`） | 下一个 tick（不用等 30 秒） |
| 司机接了又放弃 / 乘客取消后订单复活 | 下一个 tick（推送被置 `expired`，本轮作废） |

正常节奏（司机一直不回应）：

```
T+0    推给司机 A（60 秒有效）
T+15   tick：A 的推送还在 30 秒内，跳过
T+30   tick：距上次已 30 秒，推给司机 B  ← A 的推送还剩 30 秒，两人都看得到
T+45   tick：距上次 15 秒，跳过
T+60   tick：距上次 30 秒，推给司机 C；A 的推送这时候过期
...
```

司机当场拒绝时（更快）：

```
T+2    推给司机 A
T+5    A 点「拒绝」→ 推送变 rejected
T+15   tick：本单没有 30 秒内的 pending → 直接推给司机 B
```

**这段重叠是有意的**：宁可让两位司机都有机会，也不让乘客干等第一位回心转意。代价是「抢单」，由服务端的乐观锁兜住（见 5.6）。

**两层各管一件事**：

- **档位**（A/B/C/D）决定「**先推哪一批**」——A 档推完才到 B 档
- **同档**（差 < 1 分钟）决定「**这一批里先推谁**」——时间一样才比服务分

**「时间差 < 1 分钟」怎么算**：在**同一档位内**，和**最快的那个**比，不是和相邻的比。

例子：A 档里有四个司机，ETA 是 1.0 / 1.5 / 2.0 / 2.9 分钟。

- 最快 = 1.0
- 1.5 - 1.0 = 0.5 < 1 → 同档
- 2.0 - 1.0 = 1.0，不 < 1 → 不同档
- 2.9 - 1.0 = 1.9，不 < 1 → 不同档

所以 1.0 和 1.5 的司机比服务分，2.0 和 2.9 的司机这一轮出局。

**下一轮（30 秒后）**：假设这一轮推的是 1.5，他没接，1.5 记为「推过」。

```
候选 = [1.0, 2.0, 2.9]   ← 1.0 还在，它上一轮没被推过
最快 = 1.0
同档 = [1.0]（2.0 - 1.0 = 1.0，不 < 1）
推 1.0
```

**再下一轮**：

```
候选 = [2.0, 2.9]
最快 = 2.0
同档 = [2.0, 2.9]（2.9 - 2.0 = 0.9 < 1）
按服务分排序，推 2.9
```

注意：**「同档」里只会推 1 个**（`同档[0]`），不是整批都推。所以 1.0 和 1.5 里，这一轮只有一个人收到推送，另一个留到下一轮。

**为什么是 1 分钟**：这是「相同」的容忍度。差 30 秒的两个人，谁先到对乘客没区别；差 2 分钟的两个人，乘客能感觉到。1 分钟是两者之间的分界。

**「今日接单数」从哪来**：从 `trip_order` 现算，不存字段。

```sql
SELECT count(*) FROM trip_order t
 WHERE t.driver_id = d.id
   AND t.accepted_at::date = current_date
```

口径是「今天**接过**几单」，不是「今天**完成**几单」。

为什么按 `accepted_at` 算：`trip_order` 目前只有 `waiting / accepted / cancelled` 三个状态，**没有「已完成」**，所以没有 `completed_at` 可用。接了又被取消的也算——司机跑了一趟去接，这份辛苦已经发生了。

**为什么不用缓存字段**：跨天要重置、取消要回滚、并发要加锁——三个坑。现算一次是毫秒级，每 15 秒跑一次也扛得住。

**推送是串行的**：一次只推给一个司机，满 30 秒没响应再推下一个。

不是同时推给多个——那是抢单，不是派单。

> 注意：30 秒换人、推送 60 秒有效，这两个数字叠在一起意味着**有一段时间同一单会同时挂在两位司机手上**（T+30 ~ T+60）。这时确有抢单风险，靠服务端的乐观锁兜住（见 5.6）。这不是设计疏漏，是「宁可重叠、也不让乘客干等」的取舍。

注意「记录推过」不等于「从候选池移除」：司机 1 被订单 A 推过，不影响订单 B 也推给他。这两件事是独立的。

## 五、档位设计

滴滴没有分档，它是「订单进入等待找车状态，持续匹配」。

分档是我们为了控制推送节奏加的。既然用了，就按**接驾时间**分层，不按半径。

| 档位 | 接驾时间 | 含义 |
|---|---|---|
| A | ≤ 3 分钟 | 最近，优先推 |
| B | 3 ~ 6 分钟 | A 档推完才轮到 |
| C | 6 ~ 12 分钟 | |
| D | > 12 分钟 | 最远，最后考虑 |

为什么用时间不用距离？

距离本身没有意义。乘客关心的是「等多久」。将来接入真实导航，只换估算方式，分层阈值不用动。

### 5.1 推送节奏

订单会依次经过 A、B、C、D 四个档位。

每个档位里，每 30 秒推一个司机（推送有效期 60 秒），直到这个档位没人了，才进入下一个档位。

**「推哪一个」按 4.4 的规则选**：同一档位内，先找 ETA 和最快差 < 1 分钟的那批，再按服务分降序、今日接单数升序排，取第一个。

注意不是「A 档里 ETA 最小的那个」——如果 1.0 分钟和 1.5 分钟的司机差 < 1 分钟，他们算同档，此时服务分高的那个优先，哪怕他慢 30 秒。

```
第 1 轮：A 档按 4.4 规则抽 1 个
第 2 轮：A 档还有 → 再抽 1 个
...
第 N 轮：A 档空了 → B 档抽 1 个
...
```

**重叠窗口**：因为换人是 30 秒、有效期是 60 秒，T+0 推给 A、T+30 推给 B 时，A 的推送还没过期 —— 从 T+30 到 T+60 这 30 秒里，**A 和 B 的列表里都有这一单**。

这是刻意设计的：

- 不重叠（等 A 过期再推 B）→ 乘客至少要等 60 秒才见到第二个司机
- 重叠（30 秒就推 B）→ 乘客最快 30 秒就多一个可能

代价是可能抢单，由服务端的**乐观锁 + 事务**兜住（见 5.6）——同一笔订单只会有一个司机接到。

**为什么串行推送不会让乘客多等？**

因为推送是**持续**的：第 1 个司机 30 秒没接，立刻推第 2 个。乘客唯一要等的情况是「没有司机接」。

- 如果有司机愿意接，30 秒就结束了
- 如果都不接，推 1 个和推 10 个没区别——反正没人接

所以「A 档有 10 个人要推 300 秒」不是问题：这 300 秒里，只要有一个人接，就立刻停止。

### 5.2 什么时候结束 / 什么时候失效

一张表说清两件事：**订单**去哪了、**推送**怎么了。

| 事件 | 订单 | 推送 |
|---|---|---|
| 有司机接单 | 进入「前往上车点」 | 这一单的所有推送 `expired` |
| 乘客取消 | `cancelled`（**直接失效**） | 这一单的所有推送 `expired` |
| 司机放弃 | **回到订单池**，重新派给其他司机 | 这一条 `expired` |
| 推送 60 秒没响应 | 不变 | 这一条 `expired`，订单推给下一个 |
| 司机接满 3 单 | 不变 | 不再推新单给他，但**已推的仍显示到过期** |
| 司机位置超过 60 秒没更新 | 不变 | **不再推新单给他**（视为已下线），已推的仍显示到过期 |
| 两个司机同时点接单 | 只有一个人成功 | 赢家 `accepted`，其余 `expired` |
| 四个档位都推完 | 继续挂着 | 无 |

**「司机位置超过 60 秒没更新」是什么意思**：

司机出车后每 10 秒上报一次位置。如果超过 60 秒没收到，说明定位失效或者上报断了——**这时候不能假设他还在原地**，所以当作「不参加后续接单」处理。

注意这**不等于司机下线**：他的 `status` 还是 `online`，只是位置不可信。等他重新上报位置，下一轮就又能被推了。已经推给他的单不受影响（还在 60 秒有效期内，他仍然可以接）。

**「四个档位都推完」不是结束**——订单会一直挂着，每 15 秒重新算一次。如果有新司机上线（可能落在任何一档），或者有司机跑完一单（手上空出位置），他就会被推。

### 5.3 推送与订单的关系

两个维度要分开看。

**订单维度**：常态下一个订单只在一个司机手上，但**重叠窗口内会同时挂 2 个人**。

```
T=0      推给司机 1（60 秒有效）
T=30     推给司机 2（司机 1 还剩 30 秒）  ← 这里开始重叠
T=60     推给司机 3（司机 1 过期，司机 2 还剩 30 秒）
```

所以准确说法是：**同一时刻最多 2 位司机持有同一单。** 谁先接谁得，另一个的推送立刻作废。

**司机维度**：一个司机可以同时有多个订单的推送。

```
订单 A → 司机 1
订单 B → 司机 1     ← 司机 1 手上有 3 个推送
订单 C → 司机 1
```

司机接了 A，B、C 的推送**仍然有效**——它们是不同订单，各走各的 60 秒。

### 5.4 订单状态机

> **⚠️ 本节是目标设计，尚未实现。**
>
> 当前 `trip_order.status` 只有三个值：`waiting / accepted / cancelled`。
> 下面这 7 个状态里，「前往上车点 / 等待上车 / 行程中 / 结算 / 已完成」这 5 个**还没有落到库里**——接单之后统一是 `accepted`，跑完也还是 `accepted`。
>
> **直接后果**：文档写的「行程中司机不能放弃」**现在做不到**。`cancelByDriver()` 只认 `status = 'accepted'`，不区分「还在去接的路上」和「乘客已经在车上」，两种情况都能点放弃，订单直接回到 `waiting` 重派——乘客可能被晾在半路。
>
> 补齐状态机列在 §9.4。

订单从创建到结束，目标上一共 7 个状态。

```
                    ┌─────────────┐
                    │  寻找司机    │  ← 创建后进入
                    └──────┬──────┘
                           │ 有司机接单
                           ▼
                    ┌─────────────┐
                    │ 前往上车点   │
                    └──────┬──────┘
                           │ 司机到达
                           ▼
                    ┌─────────────┐
                    │  等待上车    │
                    └──────┬──────┘
                           │ 乘客上车
                           ▼
                    ┌─────────────┐
                    │   行程中     │
                    └──────┬──────┘
                           │ 到达目的地
                           ▼
                    ┌─────────────┐
                    │   结算       │
                    └──────┬──────┘
                           │ 支付完成
                           ▼
                    ┌─────────────┐
                    │   已完成     │
                    └─────────────┘

    乘客在任何状态（除已完成）都可以取消
```

**每个状态谁能操作**：

| 状态 | 谁能取消 | 取消后 |
|---|---|---|
| 寻找司机 | 乘客 | `cancelled`，推送全 `expired` |
| 前往上车点 | 乘客、司机 | 乘客取消 → `cancelled`；司机放弃 → 回「寻找司机」 |
| 等待上车 | 乘客、司机 | 同上 |
| 行程中 | 乘客 | `cancelled`（**司机不能放弃**，乘客已在车上） |
| 结算 | 乘客 | `cancelled`（司机不能取消，已经到目的地了） |
| 已完成 | 不能取消 | — |

**为什么「司机放弃」要回到「寻找司机」而不是取消**：

订单是乘客的，不是司机的。司机不接，乘客还在等，应该继续找下一个司机。

**为什么「行程中」还能取消**：

乘客可能临时改变主意（比如发现上错车）。但这会产生「空驶费」，第一期先不做，直接取消。

**为什么「结算」司机不能取消**：

车已经开到目的地了，服务已经完成，没有「不接」这一说。

### 5.5 三个常见问题

**Q1：派给第一位司机后，多久失效？**

**60 秒。**

推送写入 `dispatch_offer` 时带 `expires_at = now() + 60 秒`（`OFFER_TTL_MS = 60_000`），到点自动从 `pending` 变 `expired`。

**Q2：多久派给下一位？**

**满 30 秒就派；如果司机在这之前点了「拒绝」，下一个 tick 就换人。**

调度器每 15 秒 tick 一次（`TICK_MS = 15_000`）。判定条件是「这一单还有没有 30 秒内、状态 `pending` 的推送」（`REPUSH_AFTER_MS = 30_000`）：

- 有 → 说明这位还没回应，让这 30 秒走完
- 没有（过期了 / 被拒了 / 被作废了）→ 立刻推下一位

因为 tick 是离散的，一直不回应的情形实际间隔落在 **30 ~ 45 秒**之间。司机当场拒绝则最快 **15 秒**就换人。

这意味着 T+30 ~ T+60 这 30 秒里，**同一单同时挂在两位司机手上**——两个人都有机会接，先点的人拿到。

**Q3：四个档位都推完还没人接？**

**订单继续挂着，不会自动取消。**

之后每 15 秒继续找下一个没推过的司机，直到：

- 有司机接单
- 乘客取消
- 全城符合条件的司机都推过了 → 等新司机上线

### 5.6 抢单防护：乐观锁 + 事务

重叠窗口带来了一个必须解决的问题：**同一单同时挂在两位司机手上，两人几乎同时点「接单」**。

如果没有防护，两人都会看到「订单是 waiting」，都更新成功，最后一个人覆盖另一个人——订单被接两次，一辆车来两个司机。

服务端的做法是**事务 + 行锁 + 乐观锁**三层：

```
BEGIN
  -- 1. 锁住订单行：同一订单的并发请求在这里排队，
  --    后到的人必须等前一个人 COMMIT 才能继续
  SELECT status, driver_id FROM trip_order WHERE id = $1 FOR UPDATE

  -- 2. 排队结束后再看状态：此时已经不是 waiting 了，直接拒绝
  if status = 'accepted' and driver_id = 我 → return  （幂等）
  if status = 'accepted'                  → 409「订单已被其他司机接走」
  if status = 'cancelled'                 → 400「订单已取消」

  -- 3. 校验我确实持有一条有效推送（不能绕过列表按单号硬接）
  SELECT id FROM dispatch_offer
   WHERE order_id = $1 AND driver_id = 我
     AND status = 'pending' AND expires_at > now()
   FOR UPDATE
  if 没有 → 409「这条推送已失效，请刷新列表」

  -- 4. 手上不能超过 3 单
  if count(我的 accepted 单) >= 3 → 400「最多同时持有 3 单」

  -- 5. 乐观锁：只有仍是 waiting 才更新得动
  UPDATE trip_order SET status = 'accepted', driver_id = 我, accepted_at = now()
   WHERE id = $1 AND status = 'waiting'
  if 没更新到行 → 409

  -- 6. 我的推送置 accepted，同单其他人的推送立刻作废
  UPDATE dispatch_offer SET status = 'accepted', responded_at = now()
   WHERE order_id = $1 AND driver_id = 我
  UPDATE dispatch_offer SET status = 'expired', responded_at = NULL
   WHERE order_id = $1 AND driver_id <> 我 AND status = 'pending'
COMMIT
```

**为什么三步都要**：

| 手段 | 挡住什么 |
|---|---|
| `FOR UPDATE` 行锁 | 两人同时进事务时，强制排队，不是各看各的 |
| 状态复查 | 排队结束后发现「已经有人接了」，直接拒绝 |
| `WHERE status = 'waiting'` | 万一前两道被绕过（比如别处写了脏数据），这一道保证只改一次 |

**两条接单入口必须共用同一把锁**：

司机端有两个接口都能接单 —— `POST /drivers/:id/offers/:offerId/accept` 和 `POST /drivers/:id/orders/:orderId/accept`。如果各写一套逻辑，就会出现「A 入口锁了、B 入口照进不误」。所以 offer 那条路**直接复用** `OrdersService.accept()`，不重复实现。

**实测结果**（`D:\downloads\race-test.mjs`）：两位司机各持一条 pending 推送，并发接同一单 →

```
结果 1: 201 {"ok":true}
结果 2: 409 {"ok":false,"reason":"订单已被其他司机接走"}
数据库: trip_order accepted|00001
        dispatch_offer [ {00001, accepted}, {00002, expired} ]
```

## 六、公平机制

滴滴的做法是**订单层面**的：

> 「若某个区域乘客呼叫多而司机少，产生了乘客排队，为保证排队公平性，则按照乘客排队顺序依次进行派单。」

司机层面靠**口碑值**。

我们的做法：

| 层面 | 机制 |
|---|---|
| 订单 | 按等待时长排序，先来的先派 |
| 司机 | 接驾时间差 < 1 分钟看服务分降序；服务分也相同看今日接单数升序 |
| 兜底 | 同一订单对同一司机只推一次，不会反复骚扰 |

**优先级链条**：

```
第一优先级：接驾时间升序
  ↓ 时间差 < 1 分钟算「相同」
第二优先级：服务分降序
  ↓ 服务分也相同
第三优先级：今日接单数升序（少的优先）
```

**为什么服务分是 tiebreak 而不是权重**：滴滴文档原话「若距离相同，则会派给口碑值分数更高的司机」——口碑值是**平手规则**，不是加权因子。如果做成权重，就会出现「3 公里外的 5.0 分司机压过 200 米的 4.8 分司机」，乘客白等。

**为什么第三层是「今日接单数」而不是「空闲时长」**：空闲时长要记录「上次被推送的时间」，一旦司机频繁被推又频繁超时，这个值会被不断重置，反而不公平。今日接单数是**结果指标**——今天跑了几单，客观、不可操纵。

> 表结构里还留着 `dispatch_offer.wave` 这个列名，但它的含义已经变了：现在记的是「这一单的第几次推送」（1、2、3……），用于运营排查，跟旧的「波次半径」没有关系。改列名要动迁移脚本，暂时保留。

**三个时间参数别搞混**：

| 参数 | 值 | 管什么 |
|---|---|---|
| `TICK_MS` | 15 秒 | 调度器**多久检查一次** |
| `REPUSH_AFTER_MS` | 30 秒 | 距上次推送满多久**换下一位** |
| `OFFER_TTL_MS` | 60 秒 | 一条推送**多久过期** |

三者的关系：每 15 秒看一眼，发现「30 秒内的 pending 推送已经没有了」就推下一位。因为 30 < 60，**新推送推到的时候旧推送还没过期** —— 这就是重叠窗口，也是抢单风险的来源，由 5.6 的乐观锁兜住。司机点「拒绝」时不用等满 30 秒，下一个 tick 就换人。

如果换人周期 ≥ 推送有效期（例如 30 秒换人、30 秒有效），就不会重叠——代价是乘客要等更久才见到第二个司机。

## 八、路面距离从哪来

### 8.1 第一阶段：直线 × 1.3

两个坐标点之间先算**球面直线距离**（haversine），再乘曲折系数近似路面：

```
路面距离 = 直线距离 × 1.3        （县城经验值）
接驾时间 = 路面距离 ÷ 30 km/h
```

`apps/server/dispatch/geo.ts` 已经这么实现了：

```ts
export function distanceMeters(a: LngLat, b: LngLat): number   // haversine，米
export function etaMinutes(a: LngLat, b: LngLat): number       // distanceMeters × 1.3 ÷ 30000 × 60
```

系数从 `DispatchTuning` 读（`detourFactor: 1.3`、`averageSpeedKmh: 30`），不写死。

**为什么先这样**：

- 零成本、零延迟、无限流风险
- 县城路网简单，1.3 的误差大约 20~30%，而 3 分钟和 4 分钟的差别对排序影响有限
- 先把「排序 + 串行推送 + 15 秒一轮」这套跑通，ETA 精度是后面的事

**代价**：遇到「直线 200 米但要绕 2 公里掉头」的情况会低估接驾时间。这是已知误差，接受。

### 8.2 第二阶段：接入高德真实路面距离

项目里已有高德路径规划能力：`apps/passenger/src/route-map.ts` 用了 `AMap.Driving`，能拿到 `route.distance`（路面距离，米）和 `route.time`（路面时间，秒）。

**但这是前端 JS API**，跑在浏览器里。派单算法在后端定时跑，用不了。

后端要调高德 **Web 服务 API**：

```
GET https://restapi.amap.com/v3/direction/driving
  ?origin=107.7309,29.8631        # 司机当前位置
  &destination=107.7222,29.8873   # 乘客上车点
  &key=<Web 服务 Key>
  &strategy=0                     # 0 = 速度优先
```

返回：

```json
{
  "status": "1",
  "route": {
    "paths": [{ "distance": "3500", "duration": "420" }]
  }
}
```

`distance` 就是路面距离，`duration` 就是接驾时间。

**前置条件**：需要**新申请一个「Web 服务」类型的 Key**。现在的 Key 是「Web 端 JS API」类型，混用会报 `USERKEY_PLAT_NOMATCH`。

### 8.3 接入高德后必须做的三件事

不能无脑调，否则额度第一天就爆。

**算一笔账**：

```
每轮：    10 个等待中订单 × 20 个候选司机 = 200 次
每分钟：  200 × 4 轮 = 800 次        （tick 15 秒 → 每分钟 4 轮）
每小时：  800 × 60 = 48,000 次 = 4.8 万
每天：    48,000 × 24 = 1,152,000 次 = 115.2 万
```

**对比高德额度**：

| 额度类型 | 每天上限 | 够不够 |
|---|---|---|
| 个人开发者 | 5,000 次 | 超 **230 倍** |
| 企业开发者 | 30 万次 | 超 **3.8 倍** |

**所以粗筛是必须的，缓存是第二道**：

| 措施 | 每天调用 | 对比额度 |
|---|---|---|
| 什么都不做 | 115.2 万 | 超企业额度 **3.8 倍** |
| 只粗筛（200 → 30 对） | 17.28 万 | 企业额度**够**了 |
| 粗筛 + 缓存（命中 80%） | 3.46 万 | 个人额度仍超 **6.9 倍**，企业绰绰有余 |

换句话说：**企业额度配上粗筛就够跑**；个人额度撑不起这个量级（3.46 万 / 5,000 = 6.9 倍），只能靠降级到直线距离兜住。

> 注意：这张表按 tick 15 秒算（每分钟 4 轮）。如果哪天把 tick 调回 5 秒，次数要乘 3 —— 当初按 5 秒算出来是 345.6 万，结论会更紧张。**改 tick 记得回来重算这张表。**

**第一层：粗筛**

先用直线距离筛一遍，超过 10 公里的直接排除，不调 API。200 个对粗筛后可能只剩 30 个。

（10 公里对应 ETA 约 26 分钟，能覆盖 D 档「>12 分钟」的全部司机。如果筛得太狠，D 档就永远推不到人。）

**第二层：缓存**

```ts
const cache = new Map<string, { meters: number; seconds: number; at: number }>();
const CACHE_TTL_MS = 30_000;

function key(driver: LngLat, pickup: LngLat): string {
  // 保留 4 位小数，约 11 米精度
  return `${driver[0].toFixed(4)},${driver[1].toFixed(4)}|${pickup[0].toFixed(4)},${pickup[1].toFixed(4)}`;
}
```

30 秒内同一对直接复用。司机 10 秒上报一次位置，30 秒内基本没动，命中率很高。

**第三层：降级**

API 超时、限流、额度用完，**退回直线 × 1.3**，不让派单卡死。

```ts
async function etaWithFallback(driver: LngLat, pickup: LngLat): Promise<number> {
  try {
    return await realEtaMinutes(driver, pickup);
  } catch {
    return etaMinutes(driver, pickup);   // 直线 × 1.3
  }
}
```

**架构要求**：`etaMinutes` 必须从 `dispatch()` 内部挪出来，改成参数传进去，算法保持纯函数。

```ts
export interface DispatchInput {
  // ...现有字段
  /** 预先算好的接驾时间（分钟），key 是 driverId */
  etaMinutes: ReadonlyMap<string, number>;
}
```

这样将来换实现，算法一行不用改。

### 8.4 三个方案的取舍

| 方案 | 做法 | 代价 |
|---|---|---|
| A | 后端调高德 Web 服务 API | 需要新申请 Key，要做粗筛 + 缓存 + 降级 |
| B | 前端算好 ETA 存数据库 | 派单是后端定时跑的，前端不在场，不现实 |
| C | 直线 × 1.3 | 零成本，误差 20~30% |

**第一阶段用 C，第二阶段换 A。**

- 限行限号（保证司机接单后不经过限行区域）

这些都需要新数据（车型、司机偏好、顺路目的地、限行规则），库里目前都没有。

### 9.4 待实现：订单状态机

**现状**：`trip_order.status` 只有 `waiting / accepted / cancelled`。

**目标**：补齐 §5.4 的 7 个状态。

**为什么值得做**：「行程中司机不能放弃」这条规则靠现在的三个状态表达不出来。司机把乘客拉在半路点「放弃」，订单会回到 `waiting` 重派，乘客被晾在路边——这是真实会发生的场景。

**最小改动方案**（先不求完整 7 态）：

| 现有状态 | 改动 |
|---|---|
| `waiting` | 不动 |
| `accepted` | 保持不变，作为「已接单」的总状态 |
| **新增 `ongoing`** | 乘客上车后由司机点「开始行程」置为此状态 |
| `cancelled` | 不动 |
| **新增 `completed`** | 到达目的地并确认收款后置为此状态 |

这样只用加 2 个状态，就能区分「去接的路上」和「乘客在车上」：
- `accepted` → 司机可以放弃（订单回 `waiting`）
- `ongoing` → 司机不能放弃（乘客已在车上）

完整 7 态（含「等待上车 / 结算」）可以以后再说。

**连带要改**：
- `passenger.sql` 的 `trip_order_status_known` 约束
- `cancelByDriver()` 的 WHERE 加 `AND status = 'accepted'`（本来就只认 accepted，加了 `ongoing` 之后自然就挡住了）
- 司机端「开始行程 / 到达目的地」按钮接上状态流转
- 今日接单数口径不变（仍按 `accepted_at`）
